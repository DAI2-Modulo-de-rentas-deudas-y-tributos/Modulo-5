# Prueba M2–M5 del 3 de noviembre

Esta lista prepara la prueba real. No implica que Core o M2 hayan recibido eventos durante la validación local.

## Antes de empezar

- M2 entrega un `ticketId` UUID real de un ticket derivado a M5 y confirma el `eventId` y `correlationId` de su `ticketUpdated/ROUTED`. No crear un ticketId de ejemplo para la prueba real.
- Confirmar que el entorno de prueba usa el contrato v1.78 aprobado, la ruta de Core y la cola previstas, y que el backend apunta sólo a la base de pruebas acordada.
- Anotar el estado inicial del ticket, las filas de inbox/outbox y el registro de entrega de Core. Usar un empleado M5 autenticado con UUID de integración persistido.

## Flujo

1. Entregar el ROUTED de M2. Comprobar un único caso M5 con el mismo `ticketId` y `correlationId`, sin asignación local previa.
2. Repetir el mismo `eventId` y verificar que no se crea otro caso ni otro STARTED. Enviar después una prioridad o escalación con un `eventId` diferente: el hilo y el ROUTED causal deben conservarse.
3. Asignar el caso. Inspeccionar el JSON guardado en el outbox: `updateType=STARTED`, `data.ticketId` original, `correlationId` original, `causationId` igual al `eventId` del ROUTED aplicable y `updatedBy.id` igual al UUID del empleado.
4. Registrar PROGRESS en `IN_PROGRESS`. Verificar contenido útil en `internalMessage`, `publicMessage=null` y `causationId=null` si no hay causa externa demostrable.
5. Solicitar información y recibir INFORMATION_PROVIDED normal. Comprobar la transición y que un evento con `purpose=RECLASSIFICATION` no altere el caso operativo.
6. Devolver un caso con RETURNED usando un `reasonCode` aprobado. Confirmar que la explicación administrativa aparece sólo en `internalMessage` y que no puede volver a asignarse hasta un ROUTED de reasignación válido.
7. Probar RESOLVED y REJECTED en casos separados; probar CANCELLED por vencimiento de información y REOPENED únicamente desde un caso resuelto. Verificar que una actualización antigua según `data.updatedAt` no pisa una más reciente.
8. Reintentar una fila fallida del outbox. Comparar su `eventId` y JSON antes y después. La entrega no debe crear un hecho nuevo.

## Confirmaciones externas

- `LOCAL_ONLY` sólo registra el evento en el adaptador local; `BROKER_CONFIRMED` sólo confirma recepción del broker. Pedir a Core evidencia de ruteo y a M2 evidencia de consumo para afirmar entrega funcional.
- Si se usa `POST /api/v1/events`, registrar 202 (aceptado), 200 con `duplicate` (mismo `eventId`) y 422 (inválido) sin interpretar ninguno como consumo por M2. La deduplicación ocurre al ingresar a Core; reenviar el mismo `eventId` no vuelve a ejecutar el handler.
- Ante nack o DLQ, seguir el reintento configurado por Core y `POST /api/v1/dlq/{id}/retry` sólo con el identificador real de esa entrada. Comparar la fila de Core y el resultado final de M2.
- Comprobar en el mensaje entregado que los null de `data` se conservan y que Core puede omitir los null del envelope.
